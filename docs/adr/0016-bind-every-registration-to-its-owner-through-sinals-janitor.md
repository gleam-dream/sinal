# Bind every registration to its owner through Sinal's janitor

<a id="adr-0016"></a>

- Every registration belongs to the process that made it, its owner. Sinal's OTP application supervises one janitor process. `attach`, `observe` and `with_subscriptions` install each handler through the janitor with the calling process as the owner, and the janitor detaches the owner's handlers when the owner exits for any reason. There is no unowned registration.
- Cleanup in the registering process runs only while that process runs. An exit signal from a linked process, a supervisor shutdown or a kill terminates a process that does not trap exits without running its cleanup, and the handler then stayed in the node-wide registry, with everything its closure captured, for the life of the node. Only another process can observe that exit, so the choice was which process.
- An opt-in owner-bound attach beside an unowned `attach`, with a janitor the application supervises and passes around, was rejected. It kept the leak as the default, and it added a wiring error: registering through a janitor that is not running. The janitor therefore runs in Sinal's own application, which the `telemetry` application already precedes; a registration made where the application is not running starts it.
- The owner is the calling process, not an argument. Every caller can name itself, and a handler that must live as long as the application is attached by a long-lived supervised process. An explicit owner argument would let a caller bind a handler to a process that has nothing to do with it, and would add a second way to express the same thing.
- The janitor installs the handler itself. Installing in the caller and reporting to the janitor afterwards would leave an interval in which the owner can exit after the janitor handled its exit and before the handler is attached, and would race a replacement owner that reuses a stable identifier.
- The janitor keeps no record a crash can lose. Each handler's native configuration is `{sinal_owner, Owner, Callback}`, so the native handler table, owned by the longer-lived `telemetry` application, records every owner. A restarted janitor reads the owners back, monitors them again, and detaches the handlers of owners that exited while no janitor ran. A separate ETS table with an heir was rejected as a second copy of the same facts.
- A stable `with_id` identifier still held by an owner that has exited passes to the next owner that attaches it, so a supervisor restart of a process that attaches under a stable identifier does not depend on the order of the old owner's exit and the new attach.
- Telemetry removes a failing handler without telling the janitor, and native detach removes by identifier alone. The janitor therefore detaches an identifier for an owner only while the native configuration under it still names that owner, so a handler that another caller attached under the reused identifier is left alone.
- An attach waits for the janitor's answer with no deadline and monitors the janitor. A call with a deadline could give up while its request stayed queued; the janitor then installed a handler for which the caller held no attachment, and `with_subscriptions` rollback could not remove it. Cancelling or reconciling a queued request was rejected as a protocol for a state that need not exist: the janitor is a local supervised process, so either its answer comes or it exits, and on its exit the caller detaches any handler installed for the request before it fails.
- Every attach is one call to the janitor in addition to the native registry call, and the handler closure is copied to the janitor. Removal follows the owner's exit without being synchronous with it.
